## ① 무엇으로 붙였나

| 부분 | 쓴 것 |
|---|---|
| 서버가 하는 패스키 확인(등록 확인·서명 확인) | **라이브러리 `@simplewebauthn/server` 14.0.3** |
| 브라우저에서 패스키 만들기·서명하기 | 브라우저 표준 WebAuthn(`navigator.credentials.create / get`)을 직접 호출 (추가 라이브러리 없음) |
| 서버가 만들고 확인하는 일회용 질문, 로그인 상태(세션), 남의 자료 막기 | **직접 구현** |
| 서버·저장소 | Cloudflare Workers + D1 (무료 플랜) |

- 라이브러리가 하는 일: 기기가 보낸 등록 응답에서 공개키를 꺼내고, 로그인 때 서명이 저장된 공개키로 맞는지·질문 값과 사이트 주소(origin)가 맞는지·본인 확인(UV)을 했는지 검사합니다.
- 내가(직접 구현한 쪽이) 확인하는 일: 질문을 매번 새로 만들어 2분만 보관하고 한 번 쓰면 지우기, 틀린 요청에는 이유를 알려 주지 않고 같은 거절하기, 로그인 뒤 세션 쿠키, 계정마다 비공개 자료 가르기.
- 비밀번호는 아예 만들지 않았습니다(DB 에 비밀번호 칸이 없음).

## ② 왜 그걸 골랐나

**한 문장:** 서명 확인은 규격이 까다로워 틀리기 쉬운 부분이라 검증된 라이브러리에 맡기고, 카드 2·3이 요구하는 "서버가 만든 질문·저장된 공개키·요청 본문 기록"은 내 코드에서 그대로 보여 줄 수 있게 나머지를 직접 구현했습니다.

함께 검토했지만 고르지 않은 방법:

| 검토한 방법 | 고르지 않은 이유 |
|---|---|
| 서명 검증까지 전부 직접 구현 | 서명 형식(CBOR·인증서) 해석을 직접 하면 검증을 빠뜨리기 쉽고 시간이 더 든다 |
| 외부 로그인 서비스(예: Clerk 등) | 코드는 적지만 서버가 만든 질문, 서버에 저장된 공개키, 등록 요청 본문 기록을 우리 쪽에서 보여 주기 어렵다 |

## ④ 안 열리는 것을 확인한 기록

전체 요청·응답 원문(세션 값 가림)은 [docs/evidence/local-run.md](https://github.com/Won-22/SKT-ALEPH/blob/f2be34417fd03715f7de9dd50859e7c5200787dc/passkey/docs/evidence/local-run.md) 에 있습니다. 같은 Worker 코드를 로컬에서 시험용 가짜 기기로 돌린 결과이고, 배포된 사이트에서 내 실제 기기(아이폰의 iCloud 키체인, Google 비밀번호 관리자)로 한 확인은 [docs/evidence/live-check.md](https://github.com/Won-22/SKT-ALEPH/blob/729f6086361743ff2ecacf561a7cb58b7d4499da/passkey/docs/evidence/live-check.md) 에 있습니다. 아래 표의 상태 코드는 로컬 증거 기록에서 확인한 값이고, 네 가지 확인마다 성공한 요청과 거절된 요청을 나란히 적습니다.

| # | 확인 | 성공한 요청 | 거절된 요청 |
|---|---|---|---|
| 1 | 패스키 없이 열어 보기 | 패스키로 로그인한 뒤 `GET /api/private/items` → **200** | 로그인 없이 같은 요청 → **401** (`로그인이 필요합니다.`), 응답에 항목 없음 |
| 2 | 패스키 두 개 사용 | 첫 패스키로 로그인 → **200**, 두 번째 패스키로 로그인 → **200** (계정 `spot-a` 의 패스키 2개: iphone, google) | 일부러 틀린 서명으로 로그인 → **401**, 서버가 모르는 패스키 → **401** (같은 안내 문구) |
| 3 | 이미 쓴 질문 재사용 | 서버가 새로 준 질문으로 서명한 로그인 → **200** | 같은 서명 응답을 다시 보냄 → **401**, 같은 질문에 새로 서명해 보내도 **401**(질문은 처음 확인할 때 지워짐), 2분 지난 질문도 **401** |
| 4 | 패스키 삭제 뒤 로그인 | 지우기 전 두 패스키 모두 로그인 → **200**, 지운 뒤 남은 하나로 로그인 → **200** | 지운 패스키로 로그인 → **401**(기기에 키가 남아 있어도 서버가 모름), 그 패스키로 열어 둔 세션도 함께 끊김 → **401** |

- **실제 기기로 확인한 것(배포 사이트, 2026-10-07):** Google 비밀번호 관리자의 패스키로 로그인 → 성공(서버에 처음으로 사용 시각이 기록됨), 같은 화면에서 iCloud 키체인의 패스키(iphone)를 지움 → 하나만 남음, 지운 iCloud 패스키로 로그인 시도 → **거절**, 남은 Google 패스키로 다시 로그인 → **성공**. 등록 때는 `spot-a` 에 iphone(2026-10-06 16:46)과 google(16:50) 두 개가 서버에 저장돼 있었습니다. 단계별 표와 서버 기록은 live-check.md 에 있습니다.
- **계정 두 개(양방향):** `spot-a` 와 `spot-b` 가 각각 자기 비공개 항목 3개를 가집니다(서로 다른 내용). A 가 B 의 항목·패스키를 지우려는 요청, B 가 A 의 것을 지우려는 요청은 모두 **404**(존재 자체를 감춤), 목록에는 서로의 것이 섞이지 않고, 거절 앞뒤 건수가 같습니다. 주소(`?account_id=`)·헤더(`X-Account-Id`)·본문(`account_id`)에 다른 계정을 적어 보내도 내 자료만 돌아옵니다. 증거 기록의 "카드 5" 장.
- **거절을 만드는 소스 위치:** [`ownedItem` L231](https://github.com/Won-22/SKT-ALEPH/blob/f2be34417fd03715f7de9dd50859e7c5200787dc/passkey/src/worker.js#L231), [`ownedPasskey` L226](https://github.com/Won-22/SKT-ALEPH/blob/f2be34417fd03715f7de9dd50859e7c5200787dc/passkey/src/worker.js#L226) 가 남의 것과 없는 것을 구분하지 않고 같은 404 를 던지고, 목록은 `WHERE account_id = ?` 로 걸러집니다.
- **패스키 등록(카드 2):** 서버가 등록 질문을 만들어 보내고(요청마다 값이 다름, DB 에 2분 보관), 등록이 끝나면 `passkeys` 표에 **공개키만** 저장됩니다. 등록 요청 본문에는 공개키가 든 응답과 서명만 있고 개인키는 없습니다. 중간에 취소하면 계정·패스키는 저장되지 않고(질문만 남았다가 2분 뒤 지워짐) 화면에 "취소되었거나 시간이 지나서 아무것도 저장되지 않았습니다" 안내가 나옵니다. 패스키에는 사람이 알아볼 수 있는 이름을 붙입니다.
- **패스키를 저장한 곳(카드 2):** `spot-a` — 첫 번째는 아이폰의 **iCloud 키체인**(이름 `iphone`), 두 번째는 **Google 비밀번호 관리자**(이름 `google`), `spot-b` — 아이폰의 iCloud 키체인(이름 `Iphone Ver.2`). (`spot-a` 의 iphone 패스키는 위 "실제 기기로 확인한 것"에서 일부러 지워 지금은 google 하나가 남아 있습니다.) 개인키는 이 보관 장소 안에만 있고 서버로 오지 않습니다. (이 PC 에서는 Windows PIN 을 쓸 수 없어 Windows Hello 는 쓰지 못했습니다.)
- **패스키가 하나도 남지 않으면(카드 4):** 서버가 마지막 하나는 지우지 못하게 막습니다(409). 그래서 하나도 안 남는 상태가 생기지 않습니다. 그래도 남은 패스키가 있는 기기·보관 장소를 모두 잃으면 이 자리에 다시 들어올 복구 방법은 없습니다(⑥).
- **로그인 뒤 사람을 알아보는 것(카드 3):** 서버가 발급한 무작위 **세션 값**(쿠키 `sid`, HttpOnly·SameSite=Strict·Secure, 7일). DB 에는 그 값의 SHA-256 만 있고 원문은 없습니다. 주소창·응답 본문에는 값이 실리지 않고, 로그아웃하면 서버의 세션 행이 지워져 같은 값이 더 통하지 않습니다.
- 자동 검사 `npm test` 80개가 위 확인(틀린 서명, 쓴 질문 재사용, 만료, 다른 사이트 주소로 서명, 본인 확인 없는 서명, 계정 간 양방향 차단, 마지막 패스키 삭제 거부 등)을 포함합니다. 소유권 확인·질문 한 번만 쓰기·서명 확인을 일부러 빼 보면 해당 검사가 실제로 실패하는 것도 확인했습니다.

## ⑤ AI와 나

- **AI에게 맡긴 일**: 패스키 서버(질문 발급·공개키 저장·서명 확인·세션·남의 자료 막기)와 화면 구현, 1번 소개 페이지에 추가 블록 끼우기, 자동 검사와 증거 기록, Cloudflare 배포, 비공개 항목의 회고 두 개 초안 작성(우리가 나눈 대화를 바탕으로 AI가 쓰고 내가 확인)
- **내가 직접 판단한 일**: 만드는 방식(라이브러리 사용, 1번 페이지를 그대로 서빙하는 새 Worker)을 고른 것, 이 PC 에서 Windows PIN 을 쓸 수 없자 아이폰으로 등록하기로 한 것, 두 번째 패스키 보관 장소(Google 비밀번호 관리자)를 정한 것, 계정 두 개의 비공개 항목을 내가 실제로 준비 중인 일(프로젝트 메모, 지원 목록)로 직접 정한 것
- **AI 제안을 따르지 않은 일**: 가짜 샘플 내용으로 두고 확인만 하자는 AI 제안을 따르지 않고 실제 내용으로 바꿨다(샘플은 지움). 또 이 PC 에서 Windows PIN 을 켜자는 제안은 설정이 막혀 있어 따르지 못했다

## ⑥ 아직 못 막은 것

"다 막았다"가 아니라 아직 막지 않은 것을 적습니다.

| 아직 못 막은 것 | 왜 위험한가 |
|---|---|
| **패스키를 지울 때 다시 서명을 요구하지 않는다** (로그인한 세션만 있으면 지울 수 있다) | 누가 내 로그인 세션을 손에 넣으면 내 패스키를 지울 수 있다 |
| **기기·보관 장소를 모두 잃었을 때 복구 방법이 없다** | 남은 패스키가 있는 곳을 모두 잃으면 이 자리에 다시 들어올 수 없다(이메일 등 복구 수단을 일부러 만들지 않음) |
| 새 자리를 만들 때 "이미 있는 자리 이름"이라고 알려 준다 | 그 화면으로 어떤 자리 이름이 있는지 알아낼 수 있다(로그인 실패 안내는 이유를 알려 주지 않음) |
| **무차별 시도 횟수 제한이 없다**(질문 발급·로그인 요청) | 누군가 질문을 계속 요청하면 DB 에 질문 행이 쌓인다(만료된 질문은 다음 발급 때 지워짐) |
| **로그 남기기가 없다** | 어떤 로그인 시도나 이상한 남의 자료 접근 시도가 있었는지 서버에 기록이 없어 나중에 알 수 없다 |
| 등록하는 기기가 어떤 기기인지 검증하지 않는다(attestation 을 받지 않음) | 어떤 종류의 기기·소프트웨어든 패스키를 만들 수 있고, 패스키에 붙인 이름은 사람이 적은 글일 뿐이다 |
| 세션이 7일 고정이고 사용 중 연장·기기별 목록·강제 로그아웃 화면이 없다 | 값이 남의 손에 들어가면 만료나 내 로그아웃·패스키 삭제 때까지 쓸 수 있다 |
| 누구나 새 자리를 만들 수 있다(50개까지) | 아무나 계정을 만들 수 있는 열린 가입이다 |
